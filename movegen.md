# Универсальный генератор ходов для русских и международных шашек

Архитектура генератора ходов, построенная вокруг класса `Damboard`
(`src/pythia/damboard/damboard.py`) в его текущем виде.

## 1. Что уже даёт `Damboard`

Внутреннее представление очень удобно для movegen:

- `squares` (`src/pythia/damboard/square_builders/standard_builder.py`) —
  плоский список с «бортиком» из `SquareState.OUT_OF_BOARD`
  (`src/pythia/core/square_state.py`) по краям. Проверка «не вышел ли луч за
  доску» сводится к сравнению состояния с `OUT_OF_BOARD` — не нужны проверки
  координат.
- `board_map` — отображение номера игрового поля (1..N, FMJD-нумерация, как в
  FEN/PDN) во внутренний индекс плоского массива.
- `white_pieces` / `black_pieces` — готовые списки фигур по сторонам.
- `BoardSize.STANDARD` (8×8 — русские) и `BoardSize.BIG` (10×10 —
  международные) — сам размер уже параметризован, геометрия ходов одинакова.

Соседние по диагонали клетки получаются сдвигами по плоскому индексу:
`±(width+3)` и `±(width+1)`, где `stride = width + 2`. Благодаря бортику
сдвиг «насквозь» всегда упирается в `OUT_OF_BOARD`.

## 2. Чего не хватает `Damboard` (минимум правок)

Поля приватные (name-mangling), поэтому в `damboard.py` стоит добавить тонкий
read-only API:

- `state(ndx)` — состояние клетки по внутреннему индексу;
- `number_at(ndx)` — обратное отображение (внутренний индекс → номер поля),
  сейчас есть только прямое;
- у `white_pieces`/`black_pieces` возвращаются внутренние индексы, а не номера
  полей — стоит отдавать номера полей (для генератора и PDN-нотации это одно и
  то же множество, но в «правильных» координатах).

Мутирующие методы генератору не нужны: рабочую позицию он держит у себя
(см. ниже), `Damboard` остаётся неизменяемым источником истины.

## 3. Универсальность — правила как данные (Strategy)

Различия русских и международных шашек не алгоритмические, а параметрические.
Поэтому генератор один, а вариативность — в объекте правил:

```python
from dataclasses import dataclass
from enum import Enum, auto


class CapturePriority(Enum):
    FREE_CHOICE = auto()        # русские: любая цепочка взятия допустима
    MAX_MAJORITY = auto()       # международные: обязательное «правило большинства»


class MidCapturePromotion(Enum):
    CONTINUE_AS_MAN = auto()    # международные: если простая в ходе взятия достигла
                                # дамочного поля и далее может бить как простая шашка,
                                # она обязана это сделать и при этом остаётся простой
                                # до конца хода
    PROMOTES_AT_ONCE = auto()   # русские: простая превращается в дамку сразу, как
                                # только достигла дамочного поля, и продолжает бой
                                # уже как дамка


@dataclass(frozen=True)
class Rules:
    mid_capture_promotion: MidCapturePromotion
    capture_priority: CapturePriority
    promotion_rows: frozenset[int]  # строки превращения, считается от геометрии доски


RUSSIAN = Rules(MidCapturePromotion.PROMOTES_AT_ONCE, CapturePriority.FREE_CHOICE, ...)
INTERNATIONAL = Rules(MidCapturePromotion.CONTINUE_AS_MAN, CapturePriority.MAX_MAJORITY, ...)
```

Обратите внимание: в **обоих** вариантах пешка бьёт назад и взятие обязательно.
Однако в международных шашках действует «правило большинства»: если есть
несколько вариантов взятия, выбирать нужно тот, при котором бьётся наибольшее
количество фигур. Это влияет на дерево поиска взятий:

- при `CapturePriority.FREE_CHOICE` (русские) достаточно найти любую полную
  цепочку взятия — ветку можно обрезать на первом же листе;
- при `CapturePriority.MAX_MAJORITY` (международные) нужно перебрать **все**
  возможные цепочки взятия, зафиксировать максимум побитых фигур и оставить
  только ходы, которые его достигают (это касается и дамок: у дамки приоритет —
  максимальное число побитых, а не дальность полёта).

Практически это решается параметром правила: генератор строит полное дерево
взятий в обоих вариантах, а фильтр «оставить только ходы с максимальной длиной
`captured`» включается только для `MAX_MAJORITY`.

## 4. Структура пакета `movegen`

```
src/pythia/movegen/
    __init__.py       # экспорт MoveGenerator, Rules, RUSSIAN, INTERNATIONAL
    rules.py          # Rules + пресеты
    move.py           # Move, Step
    generator.py      # MoveGenerator(Damboard, Rules)
```

Представление хода — как последовательность шагов (нужно и для PDN, и для
анимации):

```python
@dataclass(frozen=True)
class Move:
    path: tuple[int, ...]       # номера полей: исходное → ... → конечное
    captured: tuple[int, ...]   # номера побитых полей (пусто для тихого хода)
    promotes: bool = False

    @property
    def is_capture(self) -> bool:
        return bool(self.captured)
```

## 5. Алгоритм генератора

Ключевой приём: **не мутируем `Damboard`**, а держим копию состояний
`dict[int, SquareState]` (внутренний индекс → состояние). Битую шашку помечаем
как `SquareState.TAKEN` — этот статус в энуме, судя по всему, и задуман именно
для этого. Обработка `TAKEN`-клеток при этом одинакова в обоих вариантах:
битую шашку нельзя бить повторно, нельзя перепрыгивать вторично и нельзя на
неё становиться — `TAKEN`-клетка в дальнейшей цепочке взятий является
полноценным препятствием.

Скелет:

```python
class MoveGenerator:
    def __init__(self, board: Damboard, rules: Rules):
        self._board = board
        self._rules = rules
        self._stride = board.width + 2
        self._number_of = {ndx: i + 1 for i, ndx in enumerate(board)}  # board_map наоборот
        self._states = {ndx: board.state(ndx) for ndx in self._number_of}

    def generate(self, player: Player) -> list[Move]:
        captures: list[Move] = []
        for ndx in self._pieces_of(player):
            self._captures_from(ndx, [], [], captures)
        return captures if captures else self._quiet_moves(player)

    # --- взятия: DFS по всем продолжениям ---
    def _captures_from(self, ndx, path, captured, out) -> None:
        extended = False
        for direction in (-self._stride - 1, -self._stride + 1,
                          self._stride - 1, self._stride + 1):
            victim, landings = self._victim_and_landings(ndx, direction)
            for landing in landings:
                extended = True
                self._apply(ndx, landing, victim)          # victim -> TAKEN, фигура -> landing
                self._captures_from(landing, [*path, landing],
                                    [*captured, victim], out)
                self._undo(ndx, landing, victim)           # откат

        if captured and not extended:
            out.append(self._make_move(ndx, path, captured))

    def _victim_and_landings(self, ndx, direction) -> tuple[int | None, list[int]]:
        if self._is_king(ndx):
            return self._scan_king(ndx, direction)   # скользим по лучу
        return self._scan_man(ndx, direction)        # соседняя диагональ
```

Логика `_scan_king` — сердце универсальности:

1. идём по лучу: `EMPTY` — пропускаем;
2. `TAKEN` — стоп: битую шашку нельзя перепрыгивать вторично (правило
   одинаково для русских и международных шашек);
3. своя шашка — стоп, взятия в этом направлении нет;
4. чужая — запоминаем `victim`, дальше собираем **все** пустые клетки сразу
   за ней до первого препятствия: каждая становится точкой ветвления DFS.
   Приземление дамки после взятия — общее правило для обоих вариантов: дамка
   бьёт одинаково и может остановиться на любом пустом поле за битой
   фигурой; именно это даёт «развилки» длинных ударов дамкой.

`_scan_man`: бита — сосед по диагонали, приземление — клетка строго за ней
(у обоих вариантов одинаково; на `TAKEN` приземляться нельзя в обоих).

Тихие ходы (генерируются только если взятий нет — взятие обязательно):

- **пешка** — две передние диагонали на `EMPTY`;
- **дамка** — скольжение по всем четырём диагоналям до первого препятствия.

Превращение: пешка, завершившая ход на строке из `Rules.promotion_rows`,
получает `Move.promotes = True`. Поведение пешки, достигшей дамочного поля
*в ходе* взятия, различается между вариантами и задаётся
`Rules.mid_capture_promotion`:

- `PROMOTES_AT_ONCE` (русские): пешка немедленно превращается в дамку, как
  только достигла дамочного поля (в том числе «пролетая» его), и продолжает
  бой уже как дамка;
- `CONTINUE_AS_MAN` (международные): если простая в ходе взятия достигла
  дамочного поля и далее может бить как простая шашка, она обязана это
  сделать и остаётся простой до конца хода; превращение происходит только
  по завершении хода. Если продолжить бой простой невозможно, пешка
  превращается в дамку и бой продолжается уже дамкой.

DFS это учитывает автоматически: ранг фигуры (простая/дамка) проверяется на
каждом шаге рекурсии, поэтому смена ранга посреди цепочки взятий просто
меняет результат `_victim_and_landings` для следующих шагов.

## 6. DoMove / UndoMove при поиске лучшего хода

`Move` намеренно хранит только номера полей — этого достаточно для PDN,
анимации и сортировки ходов, но **не достаточно** для самостоятельного полного
отката. Разбор по полям:

| Информация для отката | Откуда берётся |
|---|---|
| Цвет побитых фигур | восстанавливаем: побитые — всегда фигуры противника ходившей стороны |
| Исходное поле ходившей фигуры | `path[0]` |
| Конечное поле | `path[-1]` |
| Превращение | `Move.promotes` — при откате дамка возвращается в простую |
| Ранг побитых фигур (простая/дамка) | **не восстанавливается из номеров полей** |

Ранг побитых — единственная теряемая информация: побитая дамка при наивном
откате вернулась бы простой. Включать фигуры в `Move` не нужно — работает
классический движковый приём «make/unmake со стеком отката»:

- `do_move` над рабочей копией `dict[int, SquareState]` перед изменениями
  пишет в стек undo-запись: прежние `SquareState` всех затронутых клеток
  (клетки пути и побитые, до пометки `TAKEN`). `SquareState` кодирует и цвет,
  и ранг, поэтому одна структура покрывает всё, включая промежуточные
  превращения внутри цепочки взятий;
- `undo_move` снимает запись со стека и восстанавливает состояния.

Тот же приём уже используется в DFS генератора: `_apply`/`_undo` знают жертву
до её пометки `TAKEN`, поэтому откат внутри генерации ходов от `Move` не
зависит. Для перебора (`MoveGenerator` — а не `Move`) добавляются методы
`do_move`/`undo_move` со стеком; альтернатива — хранить ранги в самом `Move`
(`captured: tuple[tuple[int, Rank], ...]`) — самодостаточнее, но дублирует
данные и утяжеляет структуру, которая нужна нотации и анимации «в тонком» виде.

### 6.1. Undo-запись: структура

Undo-запись — это снимок состояний **всех клеток, которые `do_move` собирается
изменить**, снятый строго **до** мутации:

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class _UndoRecord:
    # пары (внутренний индекс, SquareState клетки до хода)
    squares: tuple[tuple[int, SquareState], ...]
```

Ключевые свойства записи:

- в ней **не бывает** `SquareState.TAKEN` и `OUT_OF_BOARD` — снапшот
  снимается с «живой» позиции до каких-либо изменений, а затрагиваются
  только игровые поля;
- элемент записи — целое значение `SquareState`, которое кодирует сразу
  **цвет и ранг** фигуры (`WHITE_MAN/WHITE_KING/BLACK_MAN/BLACK_KING`) или
  пустоту. Именно поэтому одна запись покрывает всё: и ранг побитых
  (побитая дамка вернётся дамкой), и промежуточные превращения;
- порядок пар внутри кортежа не важен, все индексы в записи различны.

### 6.2. do_move: какие клетки пишутся в запись

`do_move` затрагивает ровно `len(move.captured) + 2` клеток:

| Клетка | Что делаем | Что пишем в запись |
|---|---|---|
| `move.path[0]` | очищаем → `EMPTY` | её текущее состояние (фигура ходившей стороны) |
| `move.path[-1]` | ставим фигуру (ранг по `move.promotes`) | её текущее состояние (`EMPTY` для тихого хода; для взятия — `EMPTY` или `TAKEN`) |
| каждый `v` из `move.captured` | помечаем → `TAKEN` | её текущее состояние (фигура противника: `*_MAN` или `*_KING`) |

Порядок критичен: **сначала** собираем снапшот, **потом** мутируем:

```python
class MoveGenerator:
    def __init__(self, board: Damboard, rules: Rules):
        # ... как в п.5 ...
        self._undo_stack: list[_UndoRecord] = []

    def do_move(self, move: Move) -> None:
        touched = (
            (move.path[0], self._states[move.path[0]]),
            (move.path[-1], self._states[move.path[-1]]),
            *((v, self._states[v]) for v in move.captured),
        )
        self._undo_stack.append(_UndoRecord(touched))

        # мутация — строго после записи снапшота
        for v in move.captured:
            self._states[v] = SquareState.TAKEN
        self._states[move.path[0]] = SquareState.EMPTY
        self._states[move.path[-1]] = self._state_after(move)

    def _state_after(self, move: Move) -> SquareState:
        # цвет — ходившей стороны; ранг — KING, если move.promotes, иначе прежний
        ...
```

`_state_after` восстанавливает итоговое состояние ходившей фигуры из
`path[0]` (цвет оттуда), повышая ранг до дамки при `move.promotes = True`.
Отдельно хранить «чей был ход» и «чей цвет у побитых» не нужно: побитые —
всегда фигуры противника ходившей стороны (см. таблицу выше).

Заметка о `promotes`: промежуточные превращения внутри цепочки взятий
(русские, `PROMOTES_AT_ONCE`) происходят только в DFS генератора и там
обслуживаются `_apply`/`_undo`. В `Move` для перебора попадает уже
**завершённый** ход, поэтому `Move.promotes` отражает только итоговый ранг —
и для отката через стек этого достаточно: снапшот хранит исходное состояние
`path[0]` (простая), которое и вернётся при undo.

### 6.3. undo_move: чтение записи

Откат — тупо восстановление всех пар из снятой со стека записи:

```python
    def undo_move(self) -> None:
        for ndx, state in self._undo_stack.pop().squares:
            self._states[ndx] = state
```

Восстановление в любом порядке корректно: перекрытий между затронутыми
клетками нет (клетка пути не может одновременно быть побитой). Логику
`is_capture`/`promotes` при откате анализировать не нужно — вся информация
уже в снапшоте.

### 6.4. Пример

Международные шашки: белая дамка с поля 46 бьёт 41 (чёрная простая) и 32
(чёрная дамка), останавливается на 37.

Снапшот в стеке:

```python
_UndoRecord((
    (46, SquareState.WHITE_KING),
    (37, SquareState.EMPTY),
    (41, SquareState.BLACK_MAN),
    (32, SquareState.BLACK_KING),
))
```

После `do_move`: `46 → EMPTY`, `37 → WHITE_KING`, `41/32 → TAKEN`.
После `undo_move` все четыре клетки восстановлены в точности, включая то,
что поле 32 было именно **дамкой** — единственная информация, которую
`Move` сам по себе теряет.

### 6.5. Свойства стека и почему этого достаточно

- Хранилище — обычный `list[_UndoRecord]` с жёстким LIFO: поиск (alpha-beta)
  всегда вызывает `do_move`/`undo_move` строго парами, поэтому к корню
  дерева перебора стек гарантированно пуст. Это удобно проверять assert-ом:
  `assert not self._undo_stack` после завершения перебора (в debug-режиме).
- Стоимость записи пропорциональна длине хода (`2..k+2` маленьких кортежей),
  а не размеру доски — на порядок дешевле, чем `copy` всего `dict` состояний
  на каждый узел дерева; память освобождается `pop()`-ом, GC не нагружается
  новыми словарями.
- Стек — деталь `MoveGenerator`, наружу не торчит: `Damboard` остаётся
  неизменяемым источником истины, а «рабочая позиция» перебора живёт
  в `self._states` и откатывается стеком. Для интерфейса/UI-истории ходов
  (redo/возврат по партии) стек не предназначен — там уместнее переигрывание
  списка `Move` с чистого `Damboard`.
- Связь с DFS генератора: `_apply`/`_undo` в `_captures_from` работают без
  стека (жертва и посадка известны локально в кадре рекурсии), стек undo —
  отдельный механизм второго уровня, поверх готовых `Move`. Эти два
  механизма не пересекаются: DFS порождает ходы, `do/undo` — применяет их
  при переборе.

## 7. Итоговая таблица различий → один параметр на различие

| Отличие | Русские | Международные | Где живёт |
|---|---|---|---|
| Доска | 8×8 (`STANDARD`) | 10×10 (`BIG`) | `Damboard` |
| Приземление дамки после взятия | любое пустое поле за битой | любое пустое поле за битой | общая логика (`_scan_king`) |
| Превращение при бое через дамочное поле | превращается сразу, бьёт как дамка | обязана бить как простая, остаётся простой | `Rules.mid_capture_promotion` |
| Повторный удар по битой / перепрыгивание битой | нельзя | нельзя | общая логика (`TAKEN` — препятствие) |
| Направление боя пешкой | вперёд и назад | вперёд и назад | общая логика |
| Обязательность взятия | да | да | общая логика |

Такая схема даёт единый `MoveGenerator`: геометрию и «бортик» он берёт у
`Damboard`, а вся вариативность двух игр сводится к трём полям в `Rules`.
Добавление других вариантов (бразильские, чешские, пул) дальше — это в
основном новые пресеты `Rules`, без изменения алгоритма.
